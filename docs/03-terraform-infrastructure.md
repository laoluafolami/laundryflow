# Module 3: Infrastructure as Code with Terraform

**Goal:** replace the hand-typed commands from Module 2 with code. After this module, a new environment (or a replacement
VM after a disaster) is **one command**, identical every time.

## Concepts
* **Infrastructure as Code (IaC):** infrastructure described in text files, reviewed in pull requests, versioned in git.
* **Declarative:** you describe the *end state* ("a VM named X exists"); Terraform works out the steps.
* **Provider:** plugin that knows an API. Here `azurerm` (Azure) plus `random` (generates passwords).
* **Resource:** one thing Terraform manages (`azurerm_linux_virtual_machine`).
* **State:** Terraform's notebook of what it created. Ours lives in an **Azure Storage blob** ("remote state") so the
  pipeline and you share one truth, with versioning for recovery. Never edit it by hand; never commit it.
* **Plan → Apply:** `plan` = preview of changes, `apply` = make them. Always read the plan.
* **Module:** reusable bundle. `infra/modules/platform` is written once; `envs/staging` and `envs/prod` call it with different inputs → identical shape, different size/names.
* **Drift:** someone changes Azure by hand; code and reality disagree. `plan` reveals it.
* **Immutable infrastructure:** don't repair servers, *replace* them. This is the basis of the disaster-recovery module.
* **cloud-init:** a script the VM runs on first boot. Ours installs Docker, Caddy, Azure CLI and the deploy scripts.
* **Managed identity:** the VM has its own Azure identity (no password). It is granted exactly two permissions: read secrets from *its* Key Vault, pull images from the registry (**least privilege**).

## Step 1: Get the code onto a machine with bash
**Cloud Shell** (portal `>_` → Bash) is easiest:
```bash
git clone https://github.com/YOUR-USER/laundryflow.git
cd laundryflow
```
(Or use WSL / your Mac/Linux terminal and `az login`.)

## Step 2: Run the one-time bootstrap
This creates (a) the storage account for Terraform state and (b) a passwordless identity for GitHub Actions (OIDC),
and writes `infra/backend.hcl`. Read the script first: every line is commented.
```bash
export GITHUB_REPO="YOUR-USER/laundryflow"
./infra/bootstrap/bootstrap.sh
```
At the end it prints three values (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`). **Copy them somewhere**: you need them in Module 4.

**Concept: OIDC (workload identity federation).** The old way: create an Azure password, paste it into GitHub as a secret
(it can leak, and never expires). The modern way: GitHub proves "I am workflow X of repo Y on branch main" with a short-lived token, and
Azure was told in advance to trust exactly that. **There is no password to steal.**

Commit the generated backend file (it has no secrets). First let Terraform auto-format the code. The pipeline's `terraform fmt -check` step fails on any formatting difference, and this one command prevents that:
```bash
terraform fmt -recursive infra
git add infra && git commit -m "Add Terraform backend config" && git push
```

## Step 3: Tour the Terraform (open the files in VS Code)
| File | Creates |
|---|---|
| `infra/shared/main.tf` | Azure Container Registry (private image store) |
| `infra/modules/platform/main.tf` | network + firewall (NSG), private PostgreSQL, Key Vault + secrets, public IP, the VM, role assignments |
| `infra/modules/platform/cloud-init.yaml.tftpl` | first-boot script for the VM |
| `infra/modules/platform/files/deploy.sh` / `rollback.sh` | blue/green deploy and rollback scripts, **copied into the VM by Terraform** |
| `infra/modules/platform/monitoring.tf` | Log Analytics, Application Insights, synthetic probe, alerts (Module 5) |
| `infra/envs/staging`, `infra/envs/prod` | the two environments |

Things to notice (these are interview talking points):
* The database has **no public address**; only the VM's subnet can reach it (`public_network_access_enabled = false`).
* **Port 22 (SSH) is closed.** Deploys use `az vm run-command` through Azure's control plane, authenticated with RBAC.
  (To open SSH temporarily set `admin_cidr = "YOUR.IP/32"` and apply.)
* Passwords are generated by Terraform (`random_password`) and written straight to Key Vault. **No human ever sees or types them.**
* The public IP is a *separate* resource from the VM, so a replacement VM keeps the same address/DNS name.

## Step 4: Create the shared registry
```bash
cd infra/shared
terraform init -backend-config=../backend.hcl
terraform plan
terraform apply
```
Type `yes`. Then:
```bash
terraform output acr_name
```
**Copy the ACR name** (like `acrlaundryab12c`).

## Step 5: Create staging
```bash
cd ../envs/staging
cp terraform.tfvars.example terraform.tfvars
```
Open `terraform.tfvars` in VS Code and fill in: your public key (`cat ~/.ssh/laundryflow.pub`), your email (alerts go there) and the ACR name. Then:
```bash
terraform init -backend-config=../../backend.hcl
terraform plan
terraform apply
```
This takes ~10-15 minutes (the database is the slow part). Read the plan *before* typing `yes`: count the resources, spot the VM, the DB, the Key Vault.

When it finishes:
```bash
terraform output
```
Save `url`, `resource_group`, `vm_name`, `key_vault_name` for Module 4.

## Step 6: Verify the VM (without SSH)
```bash
az vm run-command invoke -g rg-laundry-staging -n vm-laundry-staging \
  --command-id RunShellScript --scripts "cloud-init status; docker --version; caddy version; ls /opt/laundryflow" \
  --query "value[0].message" -o tsv
```
Expect `status: done`. Now open the staging `url` in a browser: you should see **"Service is being deployed"** (HTTP 503) with a valid
HTTPS padlock. That's correct: Caddy is up with a real certificate, and the app arrives via the pipeline.

> If `cloud-init status` says `running`, wait two minutes and retry. If it says `error`, run
> `--scripts "tail -50 /var/log/cloud-init-output.log"` to see why.

## Step 7: Experiment with drift (5 minutes)
1. Azure portal → resource group `rg-laundry-staging` → the VM → **Tags** → add `owner = me` → Save.
2. `terraform plan` → Terraform reports it will **remove** the tag. The code is the source of truth.
3. Run `terraform apply` or leave it. You just saw how IaC defends against manual "snowflake" changes.

## Step 8 (optional): Read a secret yourself
```bash
KV=$(terraform output -raw key_vault_name)
az keyvault secret show --vault-name $KV --name admin-password --query value -o tsv
```
If you get *Forbidden*, give yourself read access (you are not automatically a reader):
```bash
az role assignment create --role "Key Vault Secrets User" \
  --assignee $(az ad signed-in-user show --query id -o tsv) \
  --scope $(az keyvault show -n $KV --query id -o tsv)
```
Wait a minute and retry. That value is the login password for the staging app.

✅ **Done when:** `terraform apply` succeeded for shared + staging, the staging URL shows the 503 page over HTTPS, and you can explain state, plan/apply and drift.
